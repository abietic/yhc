Dynamics

How the interface moves: frame production, surface stacking, streaming updates, animation cadence, and the performance budget that keeps it smooth. Every mechanism below either already exists in internal/tui/ (cited) or is marked as a FOLLOW-ON CANDIDATE with its source reference. Candidates are not accepted P19 slices.

Frame production how a frame is made

update pipeline
engine events ──▶ eventChan ──▶ 30fps batch (33ms / ≤64 events) ──▶ Update ──▶ View ──▶ renderer line-diff existing: app.go:2089 · performance_bench_test.go:71 enforces the ceiling
  • Event-driven, batch-coalesced. Streamed tokens accumulate for one 33ms window (or 64 events) before a single Update→View pass — a hard 30fps ceiling that already exists (streamBatchWindow, app.go:33). No additional throttle is added anywhere on the View path.
  • Several bounded clocks. A self-rescheduling 120ms App tick advances spinner, streaming, thinking, and chat animation while runtime work is active (spinner.go:36, app.go:1143-1175); it drops to 500ms polling under reduced motion. The Bubbles cursor uses its own blink command, and mascot click animation uses a 60ms tick. New idle decoration therefore needs its own visibility-gated owner.
  • Full-string View, diffed downstream. The app renders bands to strings; bubbletea v1's own renderer does line diffing to the terminal. Affordability comes from the cache stack, not from cell-level compositing (see Performance).

  • Dialogs composite back-to-front over the base via line replacement (existing); centered for pickers, bottom-docked for permission. Escape always pops the top layer first.
  • Toasts today are squatters: they render inside the status line and expire lazily — Prune() only runs when something else triggers a redraw (notifications.go:81-94), so a toast can outlive its 5s TTL. FOLLOW-ON: use a Bubble Tea-owned expiry message with an injectable clock and define a dedicated L1 overlay below dialogs; direct callback mutation and a polling-only timer are not yet accepted.
  • Completions/hints are part of the composer band (L0), clamped on-screen — no change.
  • Borrowed-and-already-had: crush's dialog grace period (200ms quiet / 1500ms max) matches our existing push grace (dialog_stack.go:53-56) — nothing to do.

  • No layout-shifting motion. Animations never change row counts mid-turn (spinner appear/disappear is the one sanctioned exception, already handled by band layout) — this is what keeps scroll anchoring stable.
  • Gradient discipline. Per-frame gradient text is confined to the spinner line, which re-renders every tick anyway. Gradient text inside chat history is explicitly rejected: it would require registering messages as HistoryAnimatableItem and paying re-render cost per frame.
  • BORROWED (crush): pause animations for off-screen items, resume on re-entry (model/chat.go:440-503) — adopt when the WORK panel animates sub-agents. Pre-rendered, content-hash-cached animation frames (anim/anim.go) — adopt if shimmer cost shows up in profiles.

Performance budget what keeps 30fps affordable

  • Cache stack (existing): per-item render cache keyed by identity+version+width with frozen finished items (chat.go:1054-1115) · whole-viewport string cache (viewDirty/viewCache) · streaming-markdown prefix cache · pooled glamour renderers per width. O(viewport) render only — the history is never fully repainted.
  • Budget rule: a frame's incremental work must stay well under the 33ms window; anything per-frame (shimmer, spinner) touches exactly one line. New animations must name their tick and their cache key, or they don't ship.
  • FOLLOW-ON (from crush): resize pre-warming — reflow only visible items during resize, then warm the width cache in batches after a 120ms settle (model/chat.go:313-339). Admit only after a local benchmark reproduces a budget failure and pins scroll-anchor/height correctness.
  • FOLLOW-ON (from crush): a CRUSH_UI_DEBUG-style render-frequency overlay behind a debug flag. Treat it as verification tooling, not a visual-identity deliverable.
  • DEFERRED: pi's synchronized output (\x1b[?2026h/l) for tear-free frames depends on renderer support in bubbletea v1 — evaluate with the bubbles/bubbletea v2 question, not in this redesign. codex's 120fps FrameRequester actor is unnecessary while our ceiling is 30fps by policy.
