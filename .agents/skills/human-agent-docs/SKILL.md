# Human and Agent Documentation

## 目标

文档的目标不是“看起来完整”，而是让读者在不被误导的前提下完成任务。
按三层顺序工作，后一层不能补救前一层：

1. **事实与所有权**：什么是 current、谁拥有行为、哪些只是计划或参考。
2. **读者任务与结构**：读者要回答什么问题，沿哪条最短路径到达答案。
3. **表达与图示**：用场景、术语铺垫、表格和图降低理解成本。

同时服务三类质量：

- 人类能快速建立心智模型、判断边界并采取下一步。
- Agent 能检索到稳定符号、事实 owner 和可执行验证。
- 维护者能看出失效信号，不把快照误当长期合同。

## 不适用

- 只需修正一个错别字或格式错误。
- 需要生成完整 API 字段参考（生成器才是事实 owner）。
- 无法读取事实来源，却要求断言当前实现——此时只能写"待验证假设"。

## 遥测准入

先按 `$skill-runtime` 判断是否需要日志。若任务始终只是本地只读审查、没有 Terra
委派、不修改文档且不运行最终 gate，则跳过；否则在首次触发动作前，以
`skill=human-agent-docs`、`kind=documentation-quality` 和实际文档 scope 启动 audit
运行。仅记录会改变结论、路由或验收的适用节点：`reader_contract_frozen`、
`facts_checked`、`structure_finished`、`audit_finished` 和 `observation_finished`。

共享 runtime 负责结构化字段最小化、Terra 三段记账、子任务/父任务/调用者工作树
三层边界、每个出口的 finish，以及日志不完整时禁止量化提效或 ROI 的规则。

## 第一层：事实与所有权

### 事实纪律（硬门槛）

1. **不伪造 current。** 标清 current / gap / plan / reference；计划、旧实现和参考证据
   不能写成当前行为。无法核实时写"待验证假设"。
2. **不掩盖多入口。** 分别确认每个入口由谁组装依赖、谁拥有执行循环、谁持久化、
   谁只做投影、谁故意绕过主循环。
3. **关键论断可复核。** 给出当前源码 owner、聚焦测试、正式决策记录或可执行命令；
   给不出就删除、缩小范围或降级为假设。
4. **区分导航锚点与验证锚点。**
   - 导航：稳定符号 + 仓库相对路径。
   - 验证：测试名、Make target、命令或可复核证据。
   行号、文件数、测试数只属于带日期的快照。
5. **不把汇总分当证据。** “8.7 分”“覆盖 95%”“A 完胜 B”不能替代原始观察、
   样本、推导过程和事实来源；有明确定义的范围指标可以保留。

涉及 YHC 源码事实时与 `$write-docs` 组合使用；后者负责源码证据、
项目治理和文档 owner，本 skill 负责读者任务与表达质量。

## 第二层：读者任务与结构

先写一句任务合同：

> `<读者>` 读完后能 `<完成的判断或动作>`；当 `<失效信号>` 出现时，本页需要更新。

一页选择一个主形态，不把四种需求混成目录：

- **教程**：帮助新人学习并完成一次练习。
- **操作指南**：帮助已有目标的读者完成任务。
- **参考**：帮助读者精确查找字段、命令、状态或映射。
- **解释**：帮助读者理解原因、边界和取舍。

组织章节时优先使用读者会提出的问题、结论或动作，例如“写文件前经过哪些安全闸”，
而不是“概述”“详解”“其他”。参考文档和清单可以按实体或检索维度组织；
不要为了问题式标题破坏查找效率。

## 第三层：表达与图示

以下七条是默认技艺，不是机械模板。偏离时说明它如何更好地服务读者任务。

1. **先给结论，再给路径。** 第一屏通常回答：这是什么、解决什么、不负责什么、
   常见下一步从哪里开始。教程可以先给学习目标，参考页可以先给查找入口。
2. **标题承担导航。** 问题、结论或动作式标题优先；只读标题应能看出主线。
3. **用场景解释因果，用枚举支持查找。** 解释机制时用一个正常路径加一个
   失败/拒绝/恢复分支和可观察结果；参考、清单、矩阵可以直接枚举。
4. **先建立直觉，再亮术语。** 首次出现的术语要有解释、上下文铺垫或定义链接；
   术语是检索钩子，不是入场券。
5. **表格只承担精确映射。** 默认控制在三列和短单元格；若每列都对应必要的
   比较维度，可以超过三列，但要提供窄屏滚动或拆表。
6. **一图只答一问。** 先写问题，再画最少节点，最后写图注边界和邻近的文字等价说明。
   “流程图约七个节点、时序图约五个参与者、出现交叉线”是拆图信号，不是硬性失败条件。
   Mermaid 使用 `accTitle` / `accDescr`，且不只靠颜色编码。
7. **主线写稳定合同，快照承载易腐细节。** 导航使用符号和仓库相对路径，
   验证使用测试或命令；行号和计数标注日期、范围与刷新方法。

## 工作流

1. **冻结任务与边界**：写任务合同、目标读者、主形态、非目标和失效信号。
2. **核对事实图**：读取生产入口与核心 owner，标注 current / gap / plan / reference；
   多入口分别核对，不从旧文档推导当前实现。
3. **选择最短结构**：先列读者问题，再决定正文、表格或图。默认 Markdown；
   仅当并排对照、筛选、折叠证据、打印或响应式呈现有实质收益时用 HTML。
4. **写作并压缩**：应用七条技艺；逐段问“它改变判断或下一步吗”，删除重复、
   无行动价值的历史和不受支持的绝对词，但保留安全边界与兼容性后果。
5. **分层验收**：
   - 硬门槛：事实、ownership、链接、可访问性、载体降级能力。
   - 启发式：首屏、标题、场景、表格和图；偏离需解释。
   - 观察任务：记录原始问题、答案、定位耗时和卡点，不只给结论或分数。
6. **隔离复核**：评审者先独立回答关键问题，再看候选文档；保存题目、匿名版本、
   原始回答和版本映射。没有这些材料，只能称“定性意见”，不能称盲测证据。
7. **按文档类型验收**：使用
   [references/review-rubric.md](references/review-rubric.md)。

结构检查可运行：

```bash
python3 .agents/skills/human-agent-docs/scripts/audit_doc.py <doc>          # 结构审计
python3 .agents/skills/human-agent-docs/scripts/audit_doc.py --strict <doc> # 结构问题作为失败
```

脚本只查结构风险，不证明语义正确。HTML 额外检查无脚本、窄屏、打印。

## 交付格式

最终说明包含：

- 读者任务、主形态、范围与失效信号；
- 关键 current 论断及其 owner / 验证锚点；
- 应用或有意偏离的技艺，以及原因；
- 删除、下沉或保留的内容；
- 原始观察记录和仍需人工判断的限制。

不用“更全面”“更专业”替代证据，也不把汇总分包装成验证结果。
