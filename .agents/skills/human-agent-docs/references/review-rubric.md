# 文档验收：硬门槛、启发式与观察证据

审阅候选文档、比较两个版本或验证本 skill 时读取本文件。不要把三类证据混在一起：

1. **硬门槛**回答“是否可信、可用”；
2. **启发式审阅**回答“是否容易理解”；
3. **观察任务**回答“真实读者能否完成任务”。

汇总分可以用于内部排序，但不能替代原始记录，也不能单独证明质量。

## 1. 硬门槛

任一项失败，先返工再讨论表达偏好。

| 门槛 | 通过条件 |
|---|---|
| current 事实 | 已从当前源码、生产 wiring、正式合同或原始数据核实 |
| 状态边界 | current / gap / plan / reference 明确，不互相冒充 |
| ownership | 多入口分别写清组装、循环、副作用、持久化和投影 owner |
| 关键论断 | 有导航锚点和与文档类型匹配的验证锚点 |
| 链接 | 仓库相对链接和外部来源可达，链接文字能说明目标 |
| 可访问性 | 标题层级、图的文字等价、非颜色编码和键盘阅读可用 |
| HTML 降级 | 关闭 JavaScript 后核心内容完整，窄屏无页面级横向滚动 |
| 范围 | 非目标、已知限制和失效信号可见 |

结构审计脚本只能发现其中一部分风险，不能证明语义正确。

## 2. 启发式审阅

以下是默认预算，不是机械否决项。偏离时记录“为何更适合当前读者任务”。

| 观察点 | 默认信号 | 合理偏离示例 |
|---|---|---|
| 首屏 | 结论、范围、下一步可见 | 教程先给学习目标；参考页先给查找入口 |
| 标题 | 问题、结论或动作式 | 字段参考按实体名组织 |
| 机制解释 | 一个正常场景加一个异常分支 | 状态矩阵直接枚举 |
| 术语 | 首次出现有铺垫或定义 | 受众已由正式前置知识限定 |
| 表格 | 约三列、短单元格 | 每列都是必要比较维度且有窄屏滚动 |
| 流程图 | 约七个节点，无多问题混画 | 单一问题确实需要更多状态 |
| 时序图 | 约五个参与者 | 安全或一致性边界要求参与者显式出现 |
| 锚点 | 符号 + 相对链接；测试/命令验证 | 一次性取证报告可使用带日期行号 |

启发式检查的目标是暴露认知负担，不是让所有文档长成同一模板。

## 3. 按文档类型选择验证锚点

“两分钟定位”不应强迫所有文档都找 Go 符号和测试。

| 文档类型 | 导航锚点 | 验证锚点 |
|---|---|---|
| 代码与架构 | 类型、函数、接口、仓库相对路径 | 聚焦测试、Make target、可执行命令 |
| 操作指南 | 任务步骤、命令或 UI 入口 | 可重复执行结果、回滚步骤、验收命令 |
| 决策记录 | 决策 ID、约束、owner | 原始数据、批准记录、替代方案证据 |
| 事故复盘 | 事件、时间线、系统边界 | 日志、指标、告警、复现或恢复证据 |
| 调研报告 | 问题、假设、来源索引 | 一手来源、样本、推导过程、限制 |
| 产品说明 | 用户任务、合同、状态 | 正式需求、验收场景、行为证据 |

## 4. 观察任务

记录事实，不记录“感觉不错”。每次记录：

- 原始任务和给读者的材料；
- 读者或 Agent 的原始回答；
- 是否完成、耗时和卡点；
- 候选版本映射与测试日期；
- 作者事后解释，单独存放，不能覆盖原始回答。

### 任务 A：首屏复述

让未参与写作的人只读首屏，复述：这份文档服务谁、结论是什么、范围是什么、
下一步去哪里。记录漏掉的要点和必须追问作者的问题。可以记录耗时，但不要把
“30 秒”当成适用于所有文档的外部标准。

### 任务 B：限时定位

抽取三个真实读者问题，只允许使用候选文档。在预设时间内记录是否找到对应章节、
导航锚点和与该文档类型匹配的验证锚点。时间阈值由任务复杂度预先声明。

### 任务 C：前向 Agent 测试

让未参与编写的 Agent 在不知道期望答案的情况下完成真实任务。保存 prompt、可见材料、
完整输出和失败点。只保存“通过/失败”摘要不构成可复核证据。

## 5. 隔离评审协议

- 作者拿到读者任务、事实来源和范围，负责候选版本。
- 评审者拿到相同事实来源，先独立回答关键问题，再查看候选文档。
- 评审者不先读作者的自评、预期结论或版本身份。
- 要称为匿名或盲评，必须保存：任务、匿名 A/B、原始回答、版本映射和日期。
- 缺少任何一项时，将结论标为“未留档定性意见”，不要包装成实验或共识。

作者与评审者隔离只能降低偏差，不能替代事实核验和样本限制说明。

## 6. 比较两个候选版本

不要先问“哪个更好”，逐项记录：

- A 独有且改变读者行动的内容；
- B 独有且降低事实或范围风险的内容；
- 两者重复且只需保留一次的内容；
- 两者都遗漏的读者问题；
- 每个保留章节服务的任务和验证锚点。

合成不是取并集，也不是让其中一个版本只负责“事实”、另一个只负责“好读”。
事实、结构和表达都需要在最终版本中闭环。

## 7. Skill 前向自检

每次实质修改 skill 后，让未参与编写的 Agent 运行下列任务，保存完整输入输出：

1. “把这份大型项目介绍改成新人可进入的导读。”——应先定任务并核 current。
2. “这段机制枚举读不进去，请改进。”——解释性文档应考虑场景；参考清单不应被强改。
3. “六张图看不懂，请改进。”——应先判断每张图的问题和边界，不只按节点数删图。
4. “根据 OpenAPI 生成完整字段参考。”——应指向生成器，不手抄为长期 owner。
5. “修正 README 的一个拼写错误。”——应直接完成，不展开完整流程。
6. “不能读源码但要写当前恢复架构。”——应拒绝伪造 current，降级为待验证假设。
7. “评审一份事故复盘。”——应要求日志、时间线或指标，而不是 Go 符号与单元测试。

发现错误时，定位到事实边界、任务结构或表达技艺中的具体缺口再修改。
